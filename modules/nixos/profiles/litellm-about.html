LiteLLM: what is served here, and why

The fleet's model gateway. Everything that talks to a language model goes through this proxy, so this page is the one place that says what is reachable and on whose hardware it runs.

Model list last reviewed: 2026-11-10

Why this list looks odd on purpose

These are not the best models money can buy. They are, deliberately, the models that would fit on a 32 GB consumer GPU — because this gateway is currently running a measurement: a month of real traffic against rentable versions of models we could host ourselves, to find out what owning the hardware would have cost and whether the output would have been good enough.

Renting a model no home box could run would answer neither question. So DeepSeek-V4, GLM-5.3, Kimi K3, MiniMax and Qwen3-Coder-480B are absent even though several of them are better. Claude stays, as the baseline to beat.

Name Upstream Used for

Claude is routed direct rather than through a reseller, funded by the Max plan's monthly Console API credit. That credit does not cover Claude Code, which still bills against the subscription.

Two things to know when reading the results

No provider serves GGUF. Our self-host targets sit at 5.1–6.2 bits per weight; providers offer fp4, fp8 and bf16. fp8 is the closest tier and is pinned in the request body, so quality measured here is a mild upper bound on what self-hosting would give.

This cannot measure prefill latency. A provider's datacentre GPU produces first tokens far faster than the card we would buy, and prefill — not generation — is what dominates long agent loops. Responsiveness here is not responsiveness we would own.

Where the numbers live

LiteLLM exports per-request cost and token counters, scraped by the monitoring server on the same host. litellm_spend_metric is real money by model; the cached-token counters say whether prompt caching is working, which is the difference between a cheap month and an expensive one.
